Experimental: it may break with a bb update.

Start a long-lived coordinating thread for a body of work, and let it hand each piece to a crew thread. Open its panel in the navigation rail and press New: bb's own new-thread composer opens, already set to a fresh worktree and auto permissions, and the goal you type starts the thread. It plans, keeps its memory in a folder of markdown files on the bb server, and starts crews: child threads that each work on their own branch, on its provider and model unless you pick others, from its brief and done-criteria, with the crew rules and the memory index in their first message. Told to propose crews and wait, it saves them as drafts instead, for you to edit and start. It messages, reads and closes its crews, and sets itself reminders, once or repeating (in two hours, at a time, every day), that wake it with its own note when they come due; it can list and cancel them. When only you can decide something, it puts a one-line question with up to five options on its board and keeps working: you choose an option or answer in your own words there, never in a form in its thread, and the panel's rail entry counts it with every crew under Needs you on the boards the panel lists. A crew ends its work with one handoff (done, blocked or gave up, with what it did, its evidence, concerns, deviations and findings), stored whole. Every done handoff is checked by an independent verifier the plugin starts itself: a hidden thread in the crew's environment, on another model when bb has one, that proves the claimed commit is checked out on a clean tree, runs what proves each done-criterion and returns a verdict with the output as evidence. When the crew has a pull request, a verdict that passed every criterion waits under Verifying until CI finishes on the claimed commit, and fails if CI fails. A crew's first failed verdict goes straight back to it: the plugin sends each failed criterion and its evidence to the crew's thread as a message from the verifier, and the crew fixes it and hands off again for a new check. A second failure goes to the coordinating thread, which messages the crew, asks you, or replaces it with a fresh crew that starts from its brief and its latest findings. The plugin then wakes the coordinating thread with a short message that names what happened and never quotes a crew; a done handoff reaches it only with its verdict, and its catch-up returns every update in full. It is also woken when a crew fails, waits on you or stops without a handoff, when a crew's pull request opens, merges or closes, its CI passes or fails, or a review approves it or asks for changes (read through gh every minute while CI runs, else every five), when you save a memory file, switch verification or answer one of its questions, and when one of its reminders comes due. A switch on the New page and on the board turns verification off for one coordinating thread, for handoffs made after it. Its Board, a tab in the thread and a page in the panel, shows that switch, why PR status is unavailable when gh can't read GitHub, its digest, its open decisions under Needs you and answered ones under Done, and every crew under Needs you, Ready for review, Verifying, Working, Landing, Idle or Done, live, each linked to its thread and to its pull request with its CI; a verified handoff waits under Ready for review with ✓, or under Landing while its pull request is open, a merged one is Done, one that failed again after its fix round or couldn't be verified under Needs you with ✗ or the reason, each with its verdict a click away (every criterion, its result and evidence, and the verifier's model), an unchecked one as Unverified, a blocked one under Needs you, and a draft under Needs you with Start and Edit, which opens its brief, model and environment in bb's composer and its done-criteria as a list. bb can't stop the coordinating thread from editing files itself, so the plugin detects it: when one of its turns ends with changed files in its own environment's working tree, read through bb's git plugin, its board shows a warning and the thread is woken to hand the change to a crew, once per number of changed files; a turn that ends with the tree clean clears the warning. It is detection, not a guarantee: a change it committed isn't seen, and nothing is blocked or reverted. Each row in the panel also opens a Memory editor over the same files; every write names the version it replaces, so neither you nor the thread can silently overwrite the other.

## What you get

- **A panel in the navigation rail.** It lists every coordinating thread bb still lists, under its project, newest first, each with bb's status glyph. A row opens its thread.
- **New, with bb's own composer.** New in the panel's title bar opens bb's new-thread composer, seeded with a fresh worktree of the default branch and auto permissions so a stray edit never lands in your checkout and no approval holds the thread. Every picker works as usual. Below it, **Verify done handoffs** is on unless you turn it off. Submit, and the thread opens.
- **A thread with a role from its first turn.** It gets rules that make it plan, delegate and track rather than code, the `coordinating` playbook skill, and its tools: `crew_catch_up`, which returns every update since its last catch-up, its board and its memory files in full, `crew_memory_read` and `crew_memory_write`, which read and write one file, `crew_start`, `crew_message`, `crew_read` and `crew_close` for its crews, `crew_remind`, which sets or cancels a reminder, and `crew_ask_user`, which puts a decision to you on its board. It keeps its plan, your standing preferences and a digest in those files. No other thread is offered these tools, and a call from one is refused.
- **Crew threads.** `crew_start` starts a child thread of the coordinating thread in a fresh worktree on its machine (or in an environment provider such as boat-sandbox), on its own branch, with auto permissions, on the coordinating thread's provider and model as they are when it starts (a draft's editor can pick others; never bb's default). Its first message holds the brief, the done-criteria (1 to 12, required), and `CREW.md` and `MEMORY.md` as they are. A crew gets the `crew-work` skill, can read the memory, and hands off with `crew_handoff`, nothing more. The coordinating thread messages it as a colleague, reads its latest answer, and closes it: resolve, stop or archive. Archiving the coordinating thread archives its crews.
- **Drafts.** Ask the coordinating thread to propose crews and wait, and `crew_start` saves each one as a draft and starts nothing. A draft waits under Needs you, headed "Draft: <title>", with **Start** and **Edit**. **Edit** opens bb's own composer under the row, holding the brief, the model and the environment, with the done-criteria as a list beside it; the composer's own send button stores them, **Cancel** drops the edit, and Esc never drops one. Each criterion grows to show its whole text; Enter starts the next one and Shift+Enter breaks the line. An open edit's brief and criteria survive a reload or a redraw until it is saved or cancelled (an unsaved model or environment pick does not: bb's composer doesn't keep it), and a draft saved elsewhere meanwhile is shown beside it. **Start** spawns the crew from what is stored, exactly as `crew_start` would, and the row moves to Working with keyboard focus on it. A double click starts one thread, and a crew that has started can't be started or edited again. A crew whose spawn bb never confirmed is a draft too, so it can be started again. `crew_catch_up` lists every draft as waiting for you.
- **Handoffs and wakes.** A crew ends its work with `crew_handoff`: done (with its commit, and its pull request if it opened one), blocked or gave up, a one-line summary, and lists of what it did, its evidence, concerns, deviations and findings (up to 50 items of 2,000 characters each). It is stored whole. The plugin then sends the coordinating thread one short message: the plugin's name in brackets, then "2 updates. Call crew_catch_up to read them in full.", then one line per update, such as `- c1 "Add retries" handed off: done`. That message holds only facts the plugin derived and what the coordinating thread wrote itself (its crews' titles, its reminders' notes and its questions to you), never a crew's own words or your answers, because it reaches the thread as if typed by you. It is sent the same way when a crew fails, waits on your answer or approval, or ends a turn without a handoff, and when you save a memory file ("The user edited PLAN.md"). It never interrupts a running turn: while one is queued behind it, the next waits, and `crew_catch_up` returns every update, whole, once. A message still queued when `crew_catch_up` has returned everything is taken back, so the thread isn't woken for updates it has read. A done handoff is announced only with its verdict, as in `- c1 "Add retries" handed off: done, failed verification`.
- **An independent verifier for every done handoff.** When a crew hands off as done, the plugin, not the coordinating thread, starts a hidden verifier thread: a child of the crew's thread, in the crew's own environment, on the coordinating thread's model if the crew runs on another, else on another provider bb can run there, else on another model of the crew's provider, else on the crew's own (which the verdict then says). Its provider and model are always chosen, never bb's default. It gets the claimed commit and the done-criteria, never the crew's report. It first proves `git rev-parse HEAD` is that commit and the tree is clean, else fails every criterion; then it runs what proves or disproves each criterion, quotes the output, and never edits, commits or pushes. It ends with `crew_verdict`: each criterion pass, fail or unverifiable with its evidence, plus findings. A verdict that skips, repeats or invents a criterion, or passes one on another commit, is refused. Pass or fail is derived, never stored, and an unverifiable criterion is not a pass. While it checks, the crew sits under Verifying. A verifier that ends a turn without a verdict is reminded once, then the crew reads "Couldn't verify" under Needs you; so does one bb wouldn't start, with bb's reason. A newer done handoff stops the older verifier and replaces its verdict. A verifier that never started because the plugin reloaded is started by the once-a-minute tick.
- **Pull requests and CI.** bb tells plugins nothing about pull requests, so on the same once-a-minute tick the plugin reads each open crew's newest pull request from its branch with `gh api graphql` on the machine running bb: one call per GitHub repository, every tick while a crew's CI runs or a verdict waits for it, else every five minutes, never for a closed crew, and not again for one whose pull request was read merged or closed until it hands off again. A crew's branch is the one bb records for its thread, else the one bb's git plugin finds checked out in its environment. It keeps the number, state, review and CI on the head commit (passing, failing with the failed checks' names, running, or no checks; a check state GitHub adds later counts as running, never as a pass). The coordinating thread is woken when a pull request opens, reopens, merges or closes, when its CI passes or fails, and when a review approves it or asks for changes, as in `- c1 "Add retries" PR #41: CI passed`; a new CI run starting wakes nobody. A done handoff that passed every criterion, when it names a pull request or one is known, waits under Verifying as "Waiting for CI on #41" until CI finishes on the very commit it claims: passing makes it verified, failing makes it a failure, which goes back to the crew naming the failed checks. No checks is not a pass: in case GitHub attaches them late, it passes as "✓ Verified, no CI checks" only once a read five minutes or more after the plugin first saw that commit still finds none; time passing or a failed read never does. When gh can't read GitHub, the board says "PR status unavailable: <why>", rows keep what was read last, and no update is recorded. A failure that may pass (GitHub unreachable, a timeout, a rate limit, an answer the plugin can't read, or anything gh doesn't explain) leaves such a verdict waiting for the next read that succeeds; only one that lasts until someone acts (gh missing, signed out or holding credentials GitHub rejects, or the project's remote not on GitHub) makes it pass as "✓ Verified, CI not checked".
- **One automatic fix round.** A crew's first failed verdict (any criterion failed or unverifiable, or CI failed on its commit) doesn't wait for the coordinating thread: the plugin sends the crew's thread one message from the verifier thread, so bb shows it as another thread's and the crew never takes it for yours. It holds each criterion that didn't pass with the verifier's evidence, and its findings. The crew fixes them, commits and hands off again, and a new verifier checks the new commit. The row says Verifying until the crew has the findings. The coordinating thread has nothing to do, so this alone doesn't wake it: it is listed, as in `- c1 "Add retries" handed off: done, failed verification, findings sent back to it (fix round 1)`, in the next doorbell and catch-up. A crew gets one such round, counted on the crew before the findings are sent and kept across reloads: its next failed verdict sends nothing back and goes to the coordinating thread, and the crew waits under Needs you as "✗ Failed verification after its fix round". A crash or reload while the findings are sent, or a send that fails without proving bb refused them (a timeout, a dropped connection, a server error), leaves nothing in bb that shows whether they arrived, so they are never sent again: the round stays spent, the crew waits under Needs you as "✗ Failed verification, its findings may or may not have reached it", and the coordinating thread is woken to read the crew's thread and decide. Only when bb refuses them before taking them, as for an archived or deleted crew thread, is the round given back, and the coordinating thread's catch-up says bb refused them. A verdict on a handoff that is no longer current (the crew was messaged or handed off again since) or of a closed crew is never sent back.
- **Replace a crew.** `crew_start` with `supersedes: "c3"` stops c3 and closes it as stopped, then starts a fresh crew from c3's title, brief, done-criteria, placement and model (the coordinating thread may give a new title, brief, criteria or placement), with c3's latest verifier findings added to its brief under "Previous attempt's verifier findings". Nothing starts while c3's thread is still stopping.
- **Reminders.** Rather than wait or poll, the coordinating thread calls `crew_remind` with a one-line note and a time: `"2m"`, `"in 2h"` or `"3d"` from now, or an ISO 8601 time with its offset, and optionally `every` (such as `"1d"`) to repeat it. A time it can't read, or a date that doesn't exist such as `2027-02-29`, is refused with the forms it accepts. The once-a-minute tick wakes it with the note when one comes due, as in `- Your reminder r1: check on c1`; a one-off is then gone, and a repeating one moves to its next time after now, so a repeating reminder missed while bb was down wakes it once, not once per miss. `crew_catch_up` lists its reminders with their ids, and `crew_remind` with `cancel: "r1"` cancels one. A reminder of an archived coordinating thread wakes nothing, and stays due until the thread is unarchived; a deleted coordinating thread's reminders are deleted. Nothing finer than a minute, and no cron expressions.

- **Decisions.** When only you can decide something, the coordinating thread calls `crew_ask_user` with a one-line question and up to five options (one line each, no two alike), or none. It returns at once and the thread keeps working, because the question never waits as a form in its thread: bb holds every message to a thread while a form waits, so no crew's handoff could wake it. The decision, `d1`, `d2`…, waits on the board under Needs you, above the crews there, with a button for each option and a field to answer in your own words (Enter sends, Shift+Enter breaks the line, and Esc doesn't leave the page while it has text). A send that fails keeps your text beside the error. Your answer moves it to Done with the answer and its time, keeping keyboard focus on it, and wakes the thread with `- The user answered your question d1: Target main or release/2?`; your answer itself reaches it only through `crew_catch_up`, which also lists the questions still waiting. A decision is answered once: a second answer, as from another window, is refused. The panel's rail entry counts everything under Needs you on every board the panel lists, decisions and crews alike, and its name says which ("3 need you: 1 decision, 2 crews"); it drops as you answer a decision or a crew leaves Needs you. A crew's own question or approval stays in the crew's thread.
- **Edits it makes itself.** Its rules say it never edits project files, and bb can't enforce that: there is no read-only mode, and a plugin can't take a provider's file tools away. So when each of its turns ends, the plugin reads its own environment's working tree through bb's git plugin. Changed files (modified, added, deleted or untracked) put "2 files changed in the Coordinator's own environment when its turn ended at 14:02 …" at the top of its board and wake it with `- Your own environment has 2 files changed after your turn: hand the change to a crew`; its `crew_catch_up` tells it to describe the change in a crew brief saved as a draft, always, never started, so a crew you start redoes it on its own branch, then ask you on its board whether to discard the changes in its environment, or to leave changes you made. It never stashes, reverts, checks out or deletes anything there, not even its own changes, since you may have edited the same files: discarding them is yours to do. A turn that ends with the same count records nothing and wakes nobody, after a reload too, because the plugin compares with the last warning it stored; a different count warns again. A turn that ends with the tree clean clears the warning, and its next catch-up says so without waking it. An environment outside git, or one bb's git plugin can't read, records nothing. It is detection, not a guarantee: a change committed, or made and undone in one turn, isn't seen, and nothing is blocked or reverted. The plugin writes nothing in that environment itself: its memory lives on the bb server.
- **A switch, not a tool.** Verification is on by default. Turn it off on the New page or at the top of the board; it applies to handoffs made after it, so turning it back on doesn't check earlier ones, and each change tells the coordinating thread. No tool can change it.
- **The Board.** A fixed tab in every coordinating thread, and a page from its row in the panel, show the verification switch, the warning of files changed in the coordinating thread's own environment while there are any, "PR status unavailable: <why>" while gh can't read GitHub, `DIGEST.md` with the time it changed, the decisions put to you, then every crew with its id, title, headline and branch, and its pull request (a link to it, its state, CI and review), under Needs you (a draft, waiting on you, failed, blocked, gave up, "✗ Failed verification after its fix round: <summary>", "✗ CI failed on #41 …" or "Couldn't verify: <summary>"), Ready for review ("✓ Verified: <summary>", or "Unverified: <summary>" when verification was off, with no open pull request), Verifying (with a link to its hidden verifier thread, or "Waiting for CI on #41: <summary>"), Working (including while it fixes a failed verdict sent back to it), Landing (as Ready for review, with its pull request open), Idle (its turn ended without a handoff) or Done (closed, its pull request merged, or its thread gone). A judged row's **Verdict** button opens the verdict under it: how many criteria passed, the commit and the model that checked them, what CI said about that commit, each criterion's result with its evidence (open for a failure, folded for a pass), the findings, and a link to the verifier thread. A handoff places its crew until the crew's thread starts another turn: type into a crew and it moves to Working, then to Idle if it ends with no new handoff. Rows move as the crews' threads change, and a row opens its thread, where you can type to the crew directly.
- **Memory you can read and edit.** Each coordinating thread has a folder of markdown files on the bb server: `MEMORY.md` (the index), `GOAL.md` (your goal), `PLAN.md`, `PREFERENCES.md`, `CREW.md`, `DIGEST.md`, and any others it adds, such as `notes/api.md`. A row's **Memory** button opens an editor over them that shows the folder's path. A save there wakes the thread. You can also edit them on the server's disk; the thread reads the new text on its next catch-up.
- **No silent overwrites.** Every write names the version of the file it replaces. If the file changed since, nothing is written: the thread gets the current text to merge into, and the editor keeps your text with the newer version beside it, for you to merge and save, or to take the newer version.

## How it works

Which thread holds which role, every crew, every handoff, every verdict and every update lives in the plugin's own SQLite database on the bb server, never in the thread's metadata, which anyone can write. bb's own report to the parent is off for crews (it cuts an answer at 4,000 characters); the plugin's thread events and handoffs replace it. A done handoff and its verdict (queued, or waived when verification is off) are written in one transaction, and every later change to a verdict is a compare-and-set, so the handoff tool, the verifier's `crew_verdict` and the tick can't move one twice. A once-a-minute tick records every reminder that is due (and moves a repeating one on, in the same transaction), starts any verifier still queued, reminds or gives up on a silent one, re-sends any update a failed send left unannounced, and forgets a queued wake message bb no longer holds, since its dispatch can be missed while the plugin reloads. A queued wake message bb gave up sending (its retries spent) is taken out of the queue, and what it announced is sent again. The board joins those crews with their threads as bb lists them on every read; bb's thread events only tell an open board to read again. The memory files sit beside that database, in `memory/<coordinator id>/`. A version is a hash of a file's content, and a write replaces the file through a temporary file and a rename, so a crash never leaves half a file.

## Not yet

Pull requests are polled, never pushed, so a change shows within a minute while CI runs or a verdict waits for it, else within five. The plugin never merges, approves or comments on a pull request.
