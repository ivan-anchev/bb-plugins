Start a long-lived coordinating thread for a body of work, and let it hand each piece to a crew thread. Open its panel in the navigation rail and press New: bb's own new-thread composer opens, already set to a fresh worktree and auto permissions, and the goal you type starts the thread. It plans, keeps its memory in a folder of markdown files on the bb server, and starts crews: child threads that each work on their own branch from its brief and done-criteria, with the crew rules and the memory index in their first message. It messages, reads and closes its crews. Its Board, a tab in the thread and a page in the panel, shows its digest and every crew under Needs you, Working, Idle or Done, live, each linked to its thread. Each row in the panel also opens a Memory editor over the same files; every write names the version it replaces, so neither you nor the thread can silently overwrite the other.

## What you get

- **A panel in the navigation rail.** It lists every coordinating thread bb still lists, under its project, newest first, each with bb's status glyph. A row opens its thread.
- **New, with bb's own composer.** New in the panel's title bar opens bb's new-thread composer, seeded with a fresh worktree of the default branch and auto permissions so a stray edit never lands in your checkout and no approval holds the thread. Every picker works as usual. Submit, and the thread opens.
- **A thread with a role from its first turn.** It gets rules that make it plan, delegate and track rather than code, the `coordinating` playbook skill, and its tools: `crew_catch_up`, which returns its board and its memory files in full, `crew_memory_read` and `crew_memory_write`, which read and write one file, and `crew_start`, `crew_message`, `crew_read` and `crew_close` for its crews. It keeps its plan, your standing preferences and a digest in those files. No other thread is offered these tools, and a call from one is refused.
- **Crew threads.** `crew_start` starts a child thread of the coordinating thread in a fresh worktree on its machine (or in an environment provider such as boat-sandbox), on its own branch, with auto permissions. Its first message holds the brief, the done-criteria (1 to 12, required), and `CREW.md` and `MEMORY.md` as they are. A crew gets the `crew-work` skill and can read the memory, nothing more. The coordinating thread messages it as a colleague, reads its latest answer, and closes it: resolve, stop or archive. Archiving the coordinating thread archives its crews.
- **The Board.** A fixed tab in every coordinating thread, and a page from its row in the panel, show `DIGEST.md` with the time it changed, then every crew with its id, title, headline and branch, under Needs you (waiting on you, failed, or never started), Working, Idle or Done. Rows move as the crews' threads change, and a row opens its thread, where you can type to the crew directly.
- **Memory you can read and edit.** Each coordinating thread has a folder of markdown files on the bb server: `MEMORY.md` (the index), `GOAL.md` (your goal), `PLAN.md`, `PREFERENCES.md`, `CREW.md`, `DIGEST.md`, and any others it adds, such as `notes/api.md`. A row's **Memory** button opens an editor over them that shows the folder's path. You can also edit them on the server's disk; the thread reads the new text on its next catch-up.
- **No silent overwrites.** Every write names the version of the file it replaces. If the file changed since, nothing is written: the thread gets the current text to merge into, and the editor keeps your text with the newer version beside it, for you to merge and save, or to take the newer version.

## How it works

Which thread holds which role, and every crew, lives in the plugin's own SQLite database on the bb server, never in the thread's metadata, which anyone can write. The board joins those crews with their threads as bb lists them on every read; bb's thread events only tell an open board to read again. The memory files sit beside that database, in `memory/<coordinator id>/`. A version is a hash of a file's content, and a write replaces the file through a temporary file and a rename, so a crash never leaves half a file.

## Not yet

Crews don't report back by themselves: bb's own report to the parent is off for them, and handoffs come later, so the coordinating thread checks its board and reads its crews. Saving in the editor doesn't wake it: it reads your edit at the start of its next turn.
