Start a long-lived coordinating thread for a body of work, and let it hand each piece to a crew thread. Open its panel in the navigation rail and press New: bb's own new-thread composer opens, already set to a fresh worktree and auto permissions, and the goal you type starts the thread. It plans, keeps its memory in a folder of markdown files on the bb server, and starts crews: child threads that each work on their own branch, on its provider and model unless you pick others, from its brief and done-criteria, with the crew rules and the memory index in their first message. Told to propose crews and wait, it saves them as drafts instead, for you to edit and start. It messages, reads and closes its crews. A crew ends its work with one handoff (done, blocked or gave up, with what it did, its evidence, concerns, deviations and findings), stored whole. The plugin then wakes the coordinating thread with a short message that names what happened and never quotes a crew, and its catch-up returns every update in full; it is also woken when a crew fails, waits on you or stops without a handoff, and when you save a memory file. Its Board, a tab in the thread and a page in the panel, shows its digest and every crew under Needs you, Ready for review, Working, Idle or Done, live, each linked to its thread; a done handoff waits under Ready for review as Unverified, a blocked one under Needs you, and a draft under Needs you with Start and Edit, which opens its brief, model and environment in bb's composer and its done-criteria as a list. Each row in the panel also opens a Memory editor over the same files; every write names the version it replaces, so neither you nor the thread can silently overwrite the other.

## What you get

- **A panel in the navigation rail.** It lists every coordinating thread bb still lists, under its project, newest first, each with bb's status glyph. A row opens its thread.
- **New, with bb's own composer.** New in the panel's title bar opens bb's new-thread composer, seeded with a fresh worktree of the default branch and auto permissions so a stray edit never lands in your checkout and no approval holds the thread. Every picker works as usual. Submit, and the thread opens.
- **A thread with a role from its first turn.** It gets rules that make it plan, delegate and track rather than code, the `coordinating` playbook skill, and its tools: `crew_catch_up`, which returns every update since its last catch-up, its board and its memory files in full, `crew_memory_read` and `crew_memory_write`, which read and write one file, and `crew_start`, `crew_message`, `crew_read` and `crew_close` for its crews. It keeps its plan, your standing preferences and a digest in those files. No other thread is offered these tools, and a call from one is refused.
- **Crew threads.** `crew_start` starts a child thread of the coordinating thread in a fresh worktree on its machine (or in an environment provider such as boat-sandbox), on its own branch, with auto permissions, on the coordinating thread's provider and model as they are when it starts (a draft's editor can pick others; never bb's default). Its first message holds the brief, the done-criteria (1 to 12, required), and `CREW.md` and `MEMORY.md` as they are. A crew gets the `crew-work` skill, can read the memory, and hands off with `crew_handoff`, nothing more. The coordinating thread messages it as a colleague, reads its latest answer, and closes it: resolve, stop or archive. Archiving the coordinating thread archives its crews.
- **Drafts.** Ask the coordinating thread to propose crews and wait, and `crew_start` saves each one as a draft and starts nothing. A draft waits under Needs you, headed "Draft: <title>", with **Start** and **Edit**. **Edit** opens bb's own composer under the row, holding the brief, the model and the environment, with the done-criteria as a list beside it; the composer's own send button stores them, **Cancel** drops the edit, and Esc never drops one. Each criterion grows to show its whole text; Enter starts the next one and Shift+Enter breaks the line. An open edit's brief and criteria survive a reload or a redraw until it is saved or cancelled (an unsaved model or environment pick does not: bb's composer doesn't keep it), and a draft saved elsewhere meanwhile is shown beside it. **Start** spawns the crew from what is stored, exactly as `crew_start` would, and the row moves to Working with keyboard focus on it. A double click starts one thread, and a crew that has started can't be started or edited again. A crew whose spawn bb never confirmed is a draft too, so it can be started again. `crew_catch_up` lists every draft as waiting for you.
- **Handoffs and wakes.** A crew ends its work with `crew_handoff`: done (with its commit, and its pull request if it opened one), blocked or gave up, a one-line summary, and lists of what it did, its evidence, concerns, deviations and findings (up to 50 items of 2,000 characters each). It is stored whole. The plugin then sends the coordinating thread one short message: the plugin's name in brackets, then "2 updates. Call crew_catch_up to read them in full.", then one line per update, such as `- c1 "Add retries" handed off: done`. That message holds only facts the plugin derived and the crews' titles, never a crew's own words, because it reaches the thread as if typed by you. It is sent the same way when a crew fails, waits on your answer or approval, or ends a turn without a handoff, and when you save a memory file ("The user edited PLAN.md"). It never interrupts a running turn: while one is queued behind it, the next waits, and `crew_catch_up` returns every update, whole, once. A message still queued when `crew_catch_up` has returned everything is taken back, so the thread isn't woken for updates it has read. A done handoff is **Unverified** until verification exists.
- **The Board.** A fixed tab in every coordinating thread, and a page from its row in the panel, show `DIGEST.md` with the time it changed, then every crew with its id, title, headline and branch, under Needs you (a draft, waiting on you, failed, blocked or gave up), Ready for review (handed off as done: "Unverified: <summary>"), Working, Idle (its turn ended without a handoff) or Done. A handoff places its crew until the crew's thread starts another turn: type into a crew and it moves to Working, then to Idle if it ends with no new handoff. Rows move as the crews' threads change, and a row opens its thread, where you can type to the crew directly.
- **Memory you can read and edit.** Each coordinating thread has a folder of markdown files on the bb server: `MEMORY.md` (the index), `GOAL.md` (your goal), `PLAN.md`, `PREFERENCES.md`, `CREW.md`, `DIGEST.md`, and any others it adds, such as `notes/api.md`. A row's **Memory** button opens an editor over them that shows the folder's path. A save there wakes the thread. You can also edit them on the server's disk; the thread reads the new text on its next catch-up.
- **No silent overwrites.** Every write names the version of the file it replaces. If the file changed since, nothing is written: the thread gets the current text to merge into, and the editor keeps your text with the newer version beside it, for you to merge and save, or to take the newer version.

## How it works

Which thread holds which role, every crew, every handoff and every update lives in the plugin's own SQLite database on the bb server, never in the thread's metadata, which anyone can write. bb's own report to the parent is off for crews (it cuts an answer at 4,000 characters); the plugin's thread events and handoffs replace it. A once-a-minute tick re-sends any update a failed send left unannounced, and forgets a queued wake message bb no longer holds, since its dispatch can be missed while the plugin reloads. A queued wake message bb gave up sending (its retries spent) is taken out of the queue, and what it announced is sent again. The board joins those crews with their threads as bb lists them on every read; bb's thread events only tell an open board to read again. The memory files sit beside that database, in `memory/<coordinator id>/`. A version is a hash of a file's content, and a write replaces the file through a temporary file and a rename, so a crash never leaves half a file.
