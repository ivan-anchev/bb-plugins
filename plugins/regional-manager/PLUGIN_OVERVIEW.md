Experimental: it may break with a bb update.

Start a regional manager: a long-lived thread that takes on a body of work, plans it as issues, and starts an agent, a child thread, on each issue; all of one manager's agents are its crew. Open its panel in the navigation rail and press New: give it a name, an optional description and an icon, and press Create, which saves it with no thread and opens its page; there bb's own new-thread composer, already set to a fresh worktree and auto permissions, takes its goal, and sending it starts the manager's thread, titled with the name, on what the composer picked, the goal its first message and its GOAL.md. The panel lists each manager by its icon, its name and its description, the ones not started yet under Not started and the others under their project; a row opens a started manager's thread, and the page of one not started yet, which edits all three, deletes it, and names it in bb's title bar. Above a started manager's composer, its icon and name open the same editor below them, while a rename in bb's sidebar renames it too. It keeps the work in its issues, what was decided about each included, and its notes and your standing rules for it in a folder of markdown files on the bb server. It writes to you answer first and in proportion to the question, and stays quiet on a wake that brings you nothing to know or decide. Each issue is numbered after a key taken from its project's name, as BBP-4 in bb-plugins, and is build work, code verified on its own branch, or research, a probe, spike, investigation or design whose result is a report; it has a description for you, a brief and done-criteria for its agent (for research, the questions its report answers), and a status the plugin derives from what its agents did: Backlog, Todo, In progress, Verifying, In review, Done or Canceled, with Needs you flagged above them when only you can act. An issue can depend on others: it is blocked while one of them is open, derived on every read and never stored, and a dependency that would close a cycle is refused; dependencies inform and never refuse, so the manager can start an agent on a blocked issue, its catch-up lists the issues ready to start, and it is woken when a merge or a handoff unblocks one, while a dependency carries nothing between issues. An issue can be split into sub-issues, one level deep: the parent never has an agent, its status rolls up from theirs, and its dependencies block them; once all of a build parent's work is merged, an independent verifier the plugin starts checks its own done-criteria on the default branch, a final check that makes it Done, while a failed one is the manager's to fix with a new sub-issue. An agent works on its own branch, in a fresh worktree or a sandbox, on the provider and model the manager names or else on the manager's own; when the manager hands an issue to a new agent, the old one is stopped, never archived, and the new one continues in its environment, on its branch with its uncommitted files and pull request, moves the work to a new environment on a branch cut from its branch (through origin, once pushed, when a sandbox is on either side), or starts clean from the default branch, with every earlier handoff and verdict in its first message; the manager also names what verifies each build issue, from the preferences you give it, and the plugin picks an independent verifier when it names none. An agent ends its work with one handoff (done, blocked or gave up, with what it did and its evidence), stored whole. A research agent's done handoff carries its report: nothing verifies it, the issue is Done at once, and the plugin saves the report as a file in the manager's memory, which the manager names in the briefs of the agents that need it; the plugin hands it to nobody. Every done handoff of build work is checked by a verifier the plugin starts itself: a hidden thread in the agent's environment, on another model than the agent's when bb has one, that runs what proves each done-criterion, with anything it asks a person declined, and returns a verdict with the output as evidence, while the plugin itself checks that the claimed commit is checked out on a clean tree. A verdict that passed waits for CI when the issue has a pull request. An agent's first failed verdict goes straight back to it as the verifier's message; a second goes to the manager. The plugin wakes the manager with a short message, hidden from you, that names what happened and never quotes an agent: on handoffs, final checks, failures, an agent waiting on you, an issue back in Todo or unblocked, pull request and CI changes read through gh, your memory edits, answers and verification switch, and its own reminders. When only you can decide something, it puts a question with up to five options on its board and keeps working; a question about an issue keeps your answer among that issue's decisions, beside those the manager records on it, and every agent started on it gets them. Its Board, a tab in its thread's side panel, shows the verification switch, its open decisions and every issue in a folding lane per status, each with its agent's thread and its pull request and CI, and what blocks it, sub-issues indented under their parent, each opening in its own tab beside the Board, or focusing the one it has, to what it is about, its parent and sub-issues, what it depends on and blocks, its criteria or questions, its decisions, a build parent's final checks, and every handoff with its verdict or its report. The board warns when the manager edits files in its own environment. Below it, Memory, a section that folds like a lane and stays folded through a reload, shows the manager's memory files as one row of cards that scrolls sideways, each previewing its file, named under it with its folder, and opens one to read and edit in place, never letting you and the thread silently overwrite each other.

## What you get

- **A panel in the navigation rail.** It lists the regional managers not started yet under **Not started**, then every other one bb still lists under its project, newest first. A row shows only the manager's icon, its name and, below them, its description. It opens the manager's thread once started, and until then its page, with the composer for its goal; an old link to a started manager's page opens its thread too. The rail entry counts everything under Needs you on every board it lists, as "3 need you: 1 decision, 2 issues".
- **A profile.** Each manager has a name, an optional description and an icon, one of 24 of bb's own. The name is its thread's title, so the sidebar and the panel always agree, and renaming it in either renames both. New asks for all three; a create with no name is refused, keeping what you typed. Until the start, **Edit** on its page changes them in place; after it, pressing the manager's icon and name above its thread's composer opens the same editor below them, where **Save** and **Cancel** close it and Esc closes one with nothing changed. An open edit survives the panel redrawing. The thread shows its name as its title, never its description. Managers started before profiles have the plugin's own icon and no description.
- **New, then the goal on its page.** New holds only the profile and **Create**, which saves the manager with no thread and opens its page: its profile, then bb's own new-thread composer asking "What should <name> get done?", set to your first project in a fresh worktree of the default branch and auto permissions, so a stray edit never lands in your checkout and no approval holds the thread. Every picker works as usual: project, environment, base branch, model, reasoning, permission mode and attachments. Sending starts the manager: its thread, titled with its name, on exactly what the composer shows, with your message as its first and, exactly as typed, its `GOAL.md`, and the page opens it. A second send of the same goal, one after the start, or one after a start whose answer bb lost, starts nothing more. Until then the manager has no thread, so nothing wakes or polls it; **Delete**, in its Edit form, asks once and removes it. Verification is on from the start; switch it on the board. A manager 0.3.0 created is upgraded by its thread's user messages: if its only one is 0.3.0's placeholder, even one that ran, it becomes one not started yet, named as that thread was, and the plugin empties the thread's queue and archives it, so send its goal from its page. One with a real message from you keeps its thread, and a missing `GOAL.md` becomes your first message there. A failed upgrade is tried again on the next tick.
- **A thread with a role from its first turn.** It gets rules that make it plan, delegate and track rather than code, the `regional-manager` playbook skill, and its tools: `crew_catch_up` (every update since its last catch-up, its board and its memory files, in full), `crew_memory_read` and `crew_memory_write`, `crew_remind`, `crew_ask_user`, `issue_create`, `issue_update` and `issue_read` for its issues, and `agent_start`, `agent_message` and `agent_stop` for its agents. No other thread is offered these tools, and a call from one is refused.
- **Issues.** `issue_create` files one, numbered after the manager's issue key, `BBP-1`, `BBP-2`…, in Todo or in Backlog, with a kind, a title, a description, and, before its agent starts, a brief and done-criteria. A build issue is code on its own branch, verified, with 1 to 12 done-criteria. A research issue is a probe, spike, investigation or design whose result is a report, with 0 to 12 questions the report answers, which nobody judges; it can't name a verifier. The kind can change only until an agent has started on the issue. The manager can change its plan at any time, rest an issue no agent holds in Backlog or Todo, cancel it, or accept one In review as Done. Every other status is derived: In progress while an agent holds it, Verifying while its done handoff is checked, In review once it passed, Done when its pull request merges. A research issue is never Verifying or In review: its done handoff makes it Done, and a message to its agent makes it In progress again until the next one.
- **Issue ids.** Every issue id is the manager's issue key and a number, as `BBP-4`. The key is up to three capital letters taken from the name of the bb project the manager works in, fixed as it starts, so renaming the project never changes an id: the first letter of each of the first three words when the name has three or more ("Acme Web App" is `AWA`), else its first three letters ("bb-plugins" is `BBP`, "ui" is `UI`), and `ISS` when it has no letters. Agents keep `a1`, decisions `d18`. A manager started before issue keys has its issues renamed as the plugin loads, each keeping its number (`i4` becomes `BBP-4`), with its parents, dependencies, agents, handoffs, checks, decisions and inbox events; text written before, in memory files, handoffs or messages, still says `i4`.
- **Dependencies.** `issue_create` takes `dependsOn`, the issues one waits for, and `issue_update` adds and removes them; `issue_read` lists what an issue depends on and what it blocks. An issue is blocked while one it depends on is not Done or Canceled, derived on every read from the same statuses the board shows, never stored; a research dependency reopened by a message to its agent blocks again until its next report. A dependency on no issue, on itself, or closing a cycle is refused, naming the cycle. Dependencies inform and never refuse: an agent can start on a blocked issue, and the start's result says what blocks it. `crew_catch_up` lists the issues ready to start (in Todo, not blocked), a merge or a handoff that unblocks an issue wakes the manager (`- BBP-3 "Card vault schema" is unblocked: BBP-2 done`), and a cancel or accept of its own says "Now ready: BBP-3" in its result. A dependency carries nothing: an agent gets another issue's report only when the manager names its file in that agent's brief.
- **Sub-issues.** `issue_create` takes a `parent`, and `issue_update` moves an issue under one or makes it top-level again; `issue_read` lists an issue's parent and sub-issues, and the catch-up lists sub-issues under their parent. One level deep: a sub-issue of a sub-issue, or a parent for an issue with sub-issues, is refused. A parent never has an agent: `agent_start` on it is refused, and an issue an agent holds can't be split. A build parent holds build and research sub-issues, a research parent research ones only. Its status rolls up: In progress once a sub-issue started, Todo while one is in Todo, else where the manager rested it; once all are closed and one is Done, a research parent is Done, and a build parent gets its final check once every Done build sub-issue is merged, flagged while one isn't. A parent is canceled only once its sub-issues are closed. Its dependencies block its sub-issues, and when its last open one closes by work, each sub-issue it unblocked wakes the manager, never the parent.
- **Agents.** `agent_start` starts a child thread of the manager on one issue, `a1`, `a2`…, in a fresh worktree on its machine or in an environment provider such as boat-sandbox (on a new branch bb makes from the default one), with auto permissions. Its first message holds the issue's description, brief and done-criteria (a research agent's under "Questions your report answers", with how to hand off its report), and `CREW.md` and `MEMORY.md` as they are. An issue has one agent at a time. An agent gets the `agent-work` skill, can read the memory, and hands off with `agent_handoff`, nothing more. Stopping an agent, or archiving or deleting its thread, ends it: its issue keeps its place if its work reached Verifying (a research issue's, Done), else returns to Todo and the manager is told. If the check of an ended agent's work then fails, the issue rests in Todo and the manager hears of the failed check. Archiving the manager archives its agents.
- **Handing an issue over.** `agent_start` on an issue that has or had an agent stops the one holding it, never archiving its thread, ends it as replaced, and starts a new agent that continues in the previous agent's environment, a worktree or a sandbox alike: the same branch, commits, uncommitted files and pull request, with a suspended sandbox woken by the start. Its first message adds where it works and every earlier handoff with its verdict's results and findings, and it gets a fix round of its own; it runs on the manager's own model unless the manager names another. `from: "default"` starts clean from the default branch instead, as a research issue's handover always does. The stopped thread keeps the environment alive until you archive it. Naming a placement moves the work instead, as does a handover after bb removed the environment (to a new one like it): a new environment on a new branch cut from the previous agent's, with its commits but not its uncommitted files, while its pull request stays on the old branch. bb cuts the branch after the start answers, so the new agent first checks that the commit the previous agent left is in its checkout, and hands off blocked if it isn't. Worktree to worktree cuts from the local branch, even once the old worktree is gone; with a sandbox on either side the branch goes through origin, allowed once its pull request's head is the commit the agent left, read fresh from GitHub at the move. The branch is the one checked out in the old environment as the move reads it, with its head; once bb removed that environment, the one on record. A move is refused before anything stops while the old environment holds uncommitted files, has no branch checked out, or can't be read (a suspended sandbox, which the read doesn't wake), and for a removed sandbox whose head never reached origin, offering a clean start; a removed worktree's unpushed commits stay on its local branch, which a new worktree reaches. The plugin never pushes, commits or copies for an agent.
- **Who runs what.** `agent_start` takes an `execution` (provider, model, optional reasoning level), and `issue_create` and `issue_update` take a build issue's `verifier`. Left out, an agent runs on the manager's own provider and model as they are when it starts, and the plugin picks the verifier: the manager's model if the agent runs on another, else another provider's default, else another model of the agent's provider, else the agent's own, which the verdict says. One bb can't run there is refused before anything starts, naming what it can run. A verifier on the agent's model, or an agent on its issue's verifier, is refused. Tell the manager your standing choice once ("build on codex gpt-5.4, verify on claude-code opus") and it names both every time.
- **Proposals.** Ask the manager to propose work and wait, and it files the issues in Backlog and describes them in one question on its board; your answer wakes it, and it starts agents on the issues you agreed to.
- **Handoffs and wakes.** An agent ends its work with `agent_handoff`: done (a build agent's with its commit, and its pull request if it opened one; a research agent's with its report, up to 20,000 characters, and no commit), blocked or gave up, a one-line summary, and lists of what it did, its evidence, concerns, deviations and findings. It is stored whole. The plugin then sends the manager one short message, as in `[Regional Manager] 2 updates. Call crew_catch_up to read them in full.` with one line per update, such as `- BBP-1 "Add retries" (a1) handed off: done, verified`. That message is hidden from you: bb shows no message for it, only the turn it starts, which folds into bb's "Worked for" row when bb collapses finished turns. It holds only facts the plugin derived and what the manager wrote itself, never an agent's words or your answers, because the manager still reads it as if typed by you. It never interrupts a running turn, and a message still queued when `crew_catch_up` has returned everything is taken back.
- **Research reports in the manager's memory.** When a research agent hands off done, the plugin saves its report to `reports/<issue id>.md` in the manager's memory folder, and `crew_catch_up` prints it whole with the file's path. You can read and edit it under Memory in the manager's Board tab, and any agent reads it with `crew_memory_read`. The plugin gives it to no agent: the manager names the file in the brief of an agent that needs it. A later report on the same issue replaces the file only while it is as the plugin saved it; a file someone edited is kept, and the new report goes beside it as `reports/<issue id>-2.md` and so on, which catch-up names. Nothing it commits or pushes is read, and the plugin never edits `MEMORY.md`.
- **An independent verifier for every done handoff of build work.** A hidden child of the agent's thread, in the agent's environment, gets the claimed commit, the done-criteria and the plugin's own read of the commit and the tree, never the agent's report. As the agent hands off, the plugin reads its environment through bb's git plugin: a HEAD other than the claimed commit, or any changed file, fails the verdict, and a read bb can't make leaves it "Couldn't verify". The verifier runs what proves or disproves each criterion, never edits, commits or pushes, and ends with `issue_verdict`: each criterion pass, fail or unverifiable with its evidence. Pass or fail is derived, and an unverifiable criterion is not a pass. A verifier that ends a turn without a verdict is reminded once. Nobody answers a verifier: anything it asks a person (a question, an approval, a connector's sign-in) is declined at once, and its verdict's findings name it; one that shows no activity for 30 minutes ends "Couldn't verify" with that reason, and the manager is woken.
- **A final check for a build parent.** A build parent's own done-criteria say what the whole is once all of it is on the default branch. When every sub-issue is closed and every Done build sub-issue's pull request merged, the parent is Verifying ("Final check due"), and within a minute the plugin starts a hidden verifier, a child of the manager's thread, in a fresh worktree of the default branch on the manager's machine, which bb starts at origin's tip ("Final check running"). It runs on the parent's named verifier unless an agent of its merged work ran on that model, else as for any check, and gets the parent's criteria and no commit: when it returns, the plugin reads its worktree through bb's git plugin and judges that commit, so only a changed file fails the tree. A pass makes the parent Done ("✓ Final check passed") and wakes whatever waited on it; a failure, or a check that couldn't run, flags it Needs you ("✗ Final check failed"), and nothing goes back to any agent: the manager files the fix as a new sub-issue, and once that is merged a new final check starts by itself, the old one kept in the record. With verification off none runs, and the parent waits In review for the manager to accept. A build parent with no done-criteria then Needs you; a research parent never has one.
- **Pull requests and CI.** bb tells plugins nothing about pull requests, so on a once-a-minute tick the plugin reads each open build issue's pull request from its branch with `gh api graphql`, and a build sub-issue's the manager accepted unmerged while its parent is open: every minute while CI runs or a verdict waits for it, else every five. It wakes the manager when a pull request opens, reopens, merges or closes, when its CI passes or fails, and when a review approves it or asks for changes. A merge makes the issue Done. A verdict that passed every criterion waits under Verifying until CI finishes on the very commit it claims: passing makes it verified, failing makes it a failure. No checks is not a pass until a read five minutes after the commit was first seen still finds none. When gh can't read GitHub, the board says "PR status unavailable: <why>".
- **One automatic fix round.** An agent's first failed verdict doesn't wait for the manager: the plugin sends the agent's thread one message from the verifier thread, with each criterion that didn't pass and its evidence. The agent fixes them and hands off again for a new check. Its next failed verdict goes to the manager, and the issue waits under Needs you. A send that may or may not have arrived is never repeated: the manager is woken to decide.
- **Reminders.** Rather than wait or poll, the manager calls `crew_remind` with a one-line note and a time (`"2m"`, `"in 2h"`, `"3d"`, or an ISO 8601 time with its offset), optionally repeating (`every: "1d"`). The tick wakes it with the note when one comes due; a repeating one missed while bb was down wakes it once. Nothing finer than a minute, and no cron expressions.
- **Decisions.** When only you can decide something, the manager calls `crew_ask_user` with a one-line question, up to five options and optionally the issue it is about. It returns at once, because a form in its thread would hold every message that could wake it. The decision waits on the board under Needs you, with a button per option and a field for your own words; your answer takes it off the board and wakes the thread, which reads your answer only through `crew_catch_up`. A question naming an issue stays, with your answer, among that issue's decisions, beside the ones the manager records on it with `issue_update`'s `decision`: what was decided and why, with the time. `issue_read`, the issue's detail on the board and the first message of every agent started on the issue show them, oldest first, the later standing where two disagree.
- **Edits it makes itself.** bb can't stop the manager from editing files, so when each of its turns ends the plugin reads its own environment's working tree through bb's git plugin. Changed files put a warning on its board and wake it to propose an issue whose agent redoes the change, and to ask you whether to discard the changes; it never touches them itself. A clean tree clears the warning. It is detection, not a guarantee: a committed change isn't seen.
- **A switch, not a tool.** Verification is on by default. Turn it off at the top of the board; it applies to handoffs made after it, and each change tells the manager.
- **The Board.** A fixed tab in every regional manager's side panel shows the switch, the edit warning, "PR status unavailable" while gh can't read GitHub, then the open decisions put to you and every issue in lanes: Needs you, In review, Verifying, In progress, Todo, Backlog, Done and Canceled, each under a bar with its glyph and count that folds it (the last three start folded). A row shows the issue's status glyph, id, kind, title and headline, its agent, which opens its thread, and its pull request with a dot for CI; a blocked issue's says "blocked by BBP-6" ahead of its headline and stays in its status's lane. Sub-issues sit indented under their parent in its lane, the parent counting them Done ("1/3") at the right of its first line, its only line when it has no headline, and a flagged one is listed under Needs you too. Pressing a row opens the issue in its own tab in the side panel, beside the Board, titled with its id and title; pressing an issue whose tab is open focuses that tab, and bb keeps the tabs across a reload. The tab changes as the board does: it heads with the issue's status, id, kind, pull request and agent, its title and headline whole, then what it is about, its parent and its sub-issues, what it depends on and what it blocks (pressing one opens that issue's tab), Done when for build work or Questions for research (left out when it has none), its Decisions (each question put to you about it with your answer, and each the manager recorded, with when), a build parent's final checks with their verdicts, and its record: each agent that held it and each handoff it made. A build handoff shows the verdict on it (each criterion's result and evidence, what CI said about the commit, the findings and a link to the verifier thread). It warns when a check had to run on the agent's own model; which model checked it is in the manager's catch-up, not on the board. A research handoff shows its report as Markdown, beside the memory file it is saved in; research has no verdict and no pull request.
- **Memory you can read and edit.** Each manager has a folder of markdown files on the bb server, made as it starts: `MEMORY.md`, `GOAL.md`, `NOTES.md` (its plan, reasoning and lessons, never what an issue already says), `RULES.md` (your standing rules for it), `CREW.md` (rules every agent follows), and any others it adds. The work itself lives in the issues, and what it tells you is its reply: there is no digest. Every manager's rules say how it writes to you: answer first, in proportion to the question, in plain words and the format that fits, and only a few words, never a recap, on a wake that brings you nothing to know or decide. A manager's memory from 0.4 is upgraded as the plugin loads, its plan and preferences files renamed to `NOTES.md` and `RULES.md`, with the headings 0.4 gave them brought up to date and every other line kept, and its digest removed; a manager that still writes an old file, or reads one that is gone, is told which one replaced it. **Memory**, at the bottom of its Board tab, lists them, each with its first line and when it last changed. Opening one shows it rendered, with **All files** to go back and **Edit**, which edits it in place with **Save** and **Cancel**; a save wakes the thread. Unsaved text stays in the browser until you save it, and a file deleted under your unsaved text stays listed, with the text, until you save or cancel it.
- **No silent overwrites.** Every write names the version of the file it replaces. If the file changed since, nothing is written: the thread gets the current text to merge into, and the editor keeps your text with the newer version beside it.

## How it works

Which thread holds which role, every issue, agent, handoff, check and update lives in the plugin's own SQLite database on the bb server, never in the thread's metadata, which anyone can write. An issue's status is never stored: the plugin derives it on every read from the issue's plan, its agents' threads as bb lists them, their handoffs, the checks and the pull request last read. bb's own report to the parent is off for agents (it cuts an answer at 4,000 characters); the plugin's thread events and handoffs replace it. A done handoff and its check are written in one transaction, and every later change to a verdict is a compare-and-set, so the handoff tool, the verifier's `issue_verdict` and the tick can't move one twice. A once-a-minute tick ends agents whose threads were archived or deleted while the plugin wasn't listening, reads pull requests, makes the final check of a build parent whose work was all merged, starts any verifier still queued, declines what a verifier asks, reminds or gives up on a silent one, records every reminder that is due, and re-sends any update a failed send left unannounced. The memory files sit beside that database, in `memory/<regional manager id>/`; a write replaces a file through a temporary file and a rename, so a crash never leaves half a file.

## Not yet

Pull requests are polled, never pushed, so a change shows within a minute while CI runs or a verdict waits for it, else within five. The plugin never merges, approves or comments on a pull request. An issue has one agent at a time. A move carries committed work only, and through origin only what the agent pushed: the plugin never pushes for it.
