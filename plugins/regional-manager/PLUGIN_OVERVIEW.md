Start a regional manager: a long-lived thread that takes on a body of work, plans it as issues, and starts an agent, a child thread, on each issue; all of one manager's agents are its crew. Open its panel in the navigation rail and press New: bb's own new-thread composer opens, already set to a fresh worktree and auto permissions, and the goal you type starts the thread. It keeps its memory in a folder of markdown files on the bb server. Each issue is build work, code verified on its own branch, or research, a probe, spike, investigation or design whose result is a report; it has a description for you, a brief and done-criteria for its agent (for research, the questions its report answers), and a status the plugin derives from what its agents did: Backlog, Todo, In progress, Verifying, In review, Done or Canceled, with Needs you flagged above them when only you can act. An agent works on its own branch, in a fresh worktree or a sandbox, on the provider and model the manager names or else on the manager's own; when the manager hands an issue to a new agent, the old one is stopped, never archived, and the new one continues in its environment, on its branch with its uncommitted files and pull request, or starts clean from the default branch, with every earlier handoff and verdict in its first message; the manager also names what verifies each build issue, from the preferences you give it, and the plugin picks an independent verifier when it names none. An agent ends its work with one handoff (done, blocked or gave up, with what it did and its evidence), stored whole. A research agent's done handoff carries its report: nothing verifies it, the issue is Done at once, and the plugin saves the report as a file in the manager's memory, which the manager names in the briefs of the agents that need it; the plugin hands it to nobody. Every done handoff of build work is checked by a verifier the plugin starts itself: a hidden thread in the agent's environment, on another model than the agent's when bb has one, that runs what proves each done-criterion and returns a verdict with the output as evidence, while the plugin itself checks that the claimed commit is checked out on a clean tree. A verdict that passed waits for CI when the issue has a pull request. An agent's first failed verdict goes straight back to it as the verifier's message; a second goes to the manager. The plugin wakes the manager with a short message that names what happened and never quotes an agent: on handoffs, failures, an agent waiting on you, an issue back in Todo, pull request and CI changes read through gh, your memory edits, answers and verification switch, and its own reminders. When only you can decide something, it puts a question with up to five options on its board and keeps working. Its Board, a tab in the thread and a page in the panel, shows the verification switch, its digest, its open decisions and every issue in a folding lane per status, each with its agent's thread and its pull request and CI, opening in place to what it is about, its criteria or questions, and every handoff with its verdict or its report. The board warns when the manager edits files in its own environment, and its Memory editor never lets you and the thread silently overwrite each other.

## What you get

- **A panel in the navigation rail.** It lists every regional manager bb still lists, under its project, newest first, each with bb's status glyph. A row opens its thread; its Board and Memory buttons open those pages. The rail entry counts everything under Needs you on every board it lists, as "3 need you: 1 decision, 2 issues".
- **New, with bb's own composer.** New opens bb's new-thread composer, seeded with a fresh worktree of the default branch and auto permissions, so a stray edit never lands in your checkout and no approval holds the thread. Every picker works as usual. Below it, **Verify done handoffs** is on unless you turn it off.
- **A thread with a role from its first turn.** It gets rules that make it plan, delegate and track rather than code, the `regional-manager` playbook skill, and its tools: `crew_catch_up` (every update since its last catch-up, its board and its memory files, in full), `crew_memory_read` and `crew_memory_write`, `crew_remind`, `crew_ask_user`, `issue_create`, `issue_update` and `issue_read` for its issues, and `agent_start`, `agent_message` and `agent_stop` for its agents. No other thread is offered these tools, and a call from one is refused.
- **Issues.** `issue_create` files one, `i1`, `i2`…, in Todo or in Backlog, with a kind, a title, a description, and, before its agent starts, a brief and done-criteria. A build issue is code on its own branch, verified, with 1 to 12 done-criteria. A research issue is a probe, spike, investigation or design whose result is a report, with 0 to 12 questions the report answers, which nobody judges; it can't name a verifier. The kind can change only until an agent has started on the issue. The manager can change its plan at any time, rest an issue no agent holds in Backlog or Todo, cancel it, or accept one In review as Done. Every other status is derived: In progress while an agent holds it, Verifying while its done handoff is checked, In review once it passed, Done when its pull request merges. A research issue is never Verifying or In review: its done handoff makes it Done, and a message to its agent makes it In progress again until the next one.
- **Agents.** `agent_start` starts a child thread of the manager on one issue, `a1`, `a2`…, in a fresh worktree on its machine or in an environment provider such as boat-sandbox (on a new branch bb makes from the default one), with auto permissions. Its first message holds the issue's description, brief and done-criteria (a research agent's under "Questions your report answers", with how to hand off its report), and `CREW.md` and `MEMORY.md` as they are. An issue has one agent at a time. An agent gets the `agent-work` skill, can read the memory, and hands off with `agent_handoff`, nothing more. Stopping an agent, or archiving or deleting its thread, ends it: its issue keeps its place if its work reached Verifying (a research issue's, Done), else returns to Todo and the manager is told. If the check of an ended agent's work then fails, the issue rests in Todo and the manager hears of the failed check. Archiving the manager archives its agents.
- **Handing an issue over.** `agent_start` on an issue that has or had an agent stops the one holding it, never archiving its thread, ends it as replaced, and starts a new agent that continues in the previous agent's environment, a worktree or a sandbox alike: the same branch, commits, uncommitted files and pull request, with a suspended sandbox woken by the start. Its first message adds where it works and every earlier handoff with its verdict's results and findings, and it gets a fix round of its own; it runs on the manager's own model unless the manager names another. `from: "default"` starts clean from the default branch instead, as a research issue's handover always does. The stopped thread keeps the environment alive until you archive it. A handover can't yet move work to a new environment: naming a placement, or continuing after bb removed the environment, is refused with the offer of a clean start.
- **Who runs what.** `agent_start` takes an `execution` (provider, model, optional reasoning level), and `issue_create` and `issue_update` take a build issue's `verifier`. Left out, an agent runs on the manager's own provider and model as they are when it starts, and the plugin picks the verifier: the manager's model if the agent runs on another, else another provider's default, else another model of the agent's provider, else the agent's own, which the verdict says. One bb can't run there is refused before anything starts, naming what it can run. A verifier on the agent's model, or an agent on its issue's verifier, is refused. Tell the manager your standing choice once ("build on codex gpt-5.4, verify on claude-code opus") and it names both every time.
- **Proposals.** Ask the manager to propose work and wait, and it files the issues in Backlog and describes them in one question on its board; your answer wakes it, and it starts agents on the issues you agreed to.
- **Handoffs and wakes.** An agent ends its work with `agent_handoff`: done (a build agent's with its commit, and its pull request if it opened one; a research agent's with its report, up to 20,000 characters, and no commit), blocked or gave up, a one-line summary, and lists of what it did, its evidence, concerns, deviations and findings. It is stored whole. The plugin then sends the manager one short message, as in `[Regional Manager] 2 updates. Call crew_catch_up to read them in full.` with one line per update, such as `- i1 "Add retries" (a1) handed off: done, verified`. That message holds only facts the plugin derived and what the manager wrote itself, never an agent's words or your answers, because it reaches the thread as if typed by you. It never interrupts a running turn, and a message still queued when `crew_catch_up` has returned everything is taken back.
- **Research reports in the manager's memory.** When a research agent hands off done, the plugin saves its report to `reports/<issue id>.md` in the manager's memory folder, and `crew_catch_up` prints it whole with the file's path. You can read and edit it in the Memory editor, and any agent reads it with `crew_memory_read`. The plugin gives it to no agent: the manager names the file in the brief of an agent that needs it. A later report on the same issue replaces the file only while it is as the plugin saved it; a file someone edited is kept, and the new report goes beside it as `reports/<issue id>-2.md` and so on, which catch-up names. Nothing it commits or pushes is read, and the plugin never edits `MEMORY.md`.
- **An independent verifier for every done handoff of build work.** A hidden child of the agent's thread, in the agent's environment, gets the claimed commit, the done-criteria and the plugin's own read of the commit and the tree, never the agent's report. As the agent hands off, the plugin reads its environment through bb's git plugin: a HEAD other than the claimed commit, or any changed file, fails the verdict, and a read bb can't make leaves it "Couldn't verify". The verifier runs what proves or disproves each criterion, never edits, commits or pushes, and ends with `issue_verdict`: each criterion pass, fail or unverifiable with its evidence. Pass or fail is derived, and an unverifiable criterion is not a pass. A verifier that ends a turn without a verdict is reminded once.
- **Pull requests and CI.** bb tells plugins nothing about pull requests, so on a once-a-minute tick the plugin reads each open build issue's pull request from its branch with `gh api graphql`: every minute while CI runs or a verdict waits for it, else every five. It wakes the manager when a pull request opens, reopens, merges or closes, when its CI passes or fails, and when a review approves it or asks for changes. A merge makes the issue Done. A verdict that passed every criterion waits under Verifying until CI finishes on the very commit it claims: passing makes it verified, failing makes it a failure. No checks is not a pass until a read five minutes after the commit was first seen still finds none. When gh can't read GitHub, the board says "PR status unavailable: <why>".
- **One automatic fix round.** An agent's first failed verdict doesn't wait for the manager: the plugin sends the agent's thread one message from the verifier thread, with each criterion that didn't pass and its evidence. The agent fixes them and hands off again for a new check. Its next failed verdict goes to the manager, and the issue waits under Needs you. A send that may or may not have arrived is never repeated: the manager is woken to decide.
- **Reminders.** Rather than wait or poll, the manager calls `crew_remind` with a one-line note and a time (`"2m"`, `"in 2h"`, `"3d"`, or an ISO 8601 time with its offset), optionally repeating (`every: "1d"`). The tick wakes it with the note when one comes due; a repeating one missed while bb was down wakes it once. Nothing finer than a minute, and no cron expressions.
- **Decisions.** When only you can decide something, the manager calls `crew_ask_user` with a one-line question, up to five options and optionally the issue it is about. It returns at once, because a form in its thread would hold every message that could wake it. The decision waits on the board under Needs you, with a button per option and a field for your own words; your answer wakes the thread, and it reads your answer only through `crew_catch_up`.
- **Edits it makes itself.** bb can't stop the manager from editing files, so when each of its turns ends the plugin reads its own environment's working tree through bb's git plugin. Changed files put a warning on its board and wake it to propose an issue whose agent redoes the change, and to ask you whether to discard the changes; it never touches them itself. A clean tree clears the warning. It is detection, not a guarantee: a committed change isn't seen.
- **A switch, not a tool.** Verification is on by default. Turn it off on the New page or at the top of the board; it applies to handoffs made after it, and each change tells the manager.
- **The Board.** A fixed tab in every regional manager, and a page from its row in the panel, show the switch, the edit warning, "PR status unavailable" while gh can't read GitHub, `DIGEST.md`, then the decisions put to you and every issue in lanes: Needs you, In review, Verifying, In progress, Todo, Backlog, Done and Canceled, each under a bar with its glyph and count that folds it (the last three start folded). A row shows the issue's status glyph, id, kind, title and headline, its agent, which opens its thread, and its pull request with a dot for CI. Pressing it opens the issue in place: what it is about, Done when for build work or Questions for research (left out when it has none), and its record: each agent that held it and each handoff it made. A build handoff shows the verdict on it (each criterion's result and evidence, what CI said about the commit, the findings and a link to the verifier thread). It warns when a check had to run on the agent's own model; which model checked it is in the manager's catch-up, not on the board. A research handoff shows its report as Markdown, beside the memory file it is saved in; research has no verdict and no pull request.
- **Memory you can read and edit.** Each manager has a folder of markdown files on the bb server: `MEMORY.md`, `GOAL.md`, `PLAN.md`, `PREFERENCES.md`, `CREW.md` (rules every agent follows), `DIGEST.md`, and any others it adds. A row's **Memory** button opens an editor over them; a save wakes the thread. Unsaved text stays in the browser until you save it.
- **No silent overwrites.** Every write names the version of the file it replaces. If the file changed since, nothing is written: the thread gets the current text to merge into, and the editor keeps your text with the newer version beside it.

## How it works

Which thread holds which role, every issue, agent, handoff, check and update lives in the plugin's own SQLite database on the bb server, never in the thread's metadata, which anyone can write. An issue's status is never stored: the plugin derives it on every read from the issue's plan, its agents' threads as bb lists them, their handoffs, the checks and the pull request last read. bb's own report to the parent is off for agents (it cuts an answer at 4,000 characters); the plugin's thread events and handoffs replace it. A done handoff and its check are written in one transaction, and every later change to a verdict is a compare-and-set, so the handoff tool, the verifier's `issue_verdict` and the tick can't move one twice. A once-a-minute tick ends agents whose threads were archived or deleted while the plugin wasn't listening, reads pull requests, starts any verifier still queued, reminds or gives up on a silent one, records every reminder that is due, and re-sends any update a failed send left unannounced. The memory files sit beside that database, in `memory/<regional manager id>/`; a write replaces a file through a temporary file and a rename, so a crash never leaves half a file.

## Not yet

Pull requests are polled, never pushed, so a change shows within a minute while CI runs or a verdict waits for it, else within five. The plugin never merges, approves or comments on a pull request. An issue has one agent at a time, and a handover can only continue in the previous agent's environment or start clean.
