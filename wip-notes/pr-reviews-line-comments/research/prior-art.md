# Prior art: line-range PR review comments (single/multi-line, fallback)

Method: shallow clones read at the SHAs below; GitHub docs fetched 2026-11-09. All three projects are MIT, pushed within the last week, 2.6k–9.7k stars.
Bar check: gh-dash (12.7k stars) was checked and **does not qualify as prior art** — `grep` of its Go source finds no inline/line review comment, `start_line`, or `pulls/*/comments` code (it opens comments/reviews through `gh`/browser). Nothing to report from it.

## GitHub REST docs (the contract)
- Create a review comment: <https://docs.github.com/en/rest/pulls/comments?apiVersion=2022-11-28#create-a-review-comment-for-a-pull-request> (`POST /repos/{owner}/{repo}/pulls/{pull_number}/comments`)
  - Required: `body`, `commit_id`, `path`. `line` is required unless `subject_type` is `file`.
  - `side` `LEFT` (deletions) | `RIGHT` (additions and unchanged context). For multi-line, `side` is the side of the *last* line.
  - Multi-line: `start_line` + `start_side` (`LEFT|RIGHT`), `line` = last line of the range. Both required for multi-line unless `in_reply_to`.
  - `subject_type`: `line` | `file`. `position` is deprecated ("closing down, use line").
  - `commit_id`: "If it isn't the latest commit, a later commit that changes the specified line can make the comment outdated."
  - Responses: 201, 403, **422 "Validation failed, or the endpoint has been spammed"**. Secondary rate limit if content is created too fast.
  - The docs do not spell out the "line must be part of the diff" message; I did not find it quoted in any of the three repos either.
- Create an issue comment (general PR comment): <https://docs.github.com/en/rest/issues/comments?apiVersion=2022-11-28#create-an-issue-comment> (`POST /repos/{owner}/{repo}/issues/{issue_number}/comments`). Only param `body`. A PR number works as `issue_number` ("Every pull request is an issue"). Responses 201/403/404/410/422. It has no path/line anchor.

## reviewdog/reviewdog — <https://github.com/reviewdog/reviewdog> (9.7k★, MIT, SHA e784ef0)
Closest match to "line comment with fallback", but it is a CI tool (no UI).
- **Calls** (go-github, REST), `service/github/github.go`:
  - Line/range comments are batched into one **review**: `PullRequests.CreateReview` with `CommitID: &g.sha`, `Event: "COMMENT"`, `Comments: [...]` — [github.go:196-202](https://github.com/reviewdog/reviewdog/blob/e784ef04b42944a329d856c69431b8db400479a6/service/github/github.go#L196-L202). So a submitted review, not standalone and not left pending.
  - Per-comment shape `buildDraftReviewComment` — [github.go:258-271](https://github.com/reviewdog/reviewdog/blob/e784ef04b42944a329d856c69431b8db400479a6/service/github/github.go#L258-L271): `Path`, `Side: "RIGHT"` always, `Line: endLine`; **only if startLine < endLine** it adds `StartLine` + `StartSide: "RIGHT"` (comment: "Start line must precede the end line"). Single-line sends no start_*.
  - Not-in-diff comments use **standalone** `PullRequests.CreateComment` with `subject_type: "file"`, `Side: RIGHT`, `CommitID` — `buildPullRequestFileComment`, [github.go:273-281](https://github.com/reviewdog/reviewdog/blob/e784ef04b42944a329d856c69431b8db400479a6/service/github/github.go#L273-L281); posted in a loop at [github.go:213-223](https://github.com/reviewdog/reviewdog/blob/e784ef04b42944a329d856c69431b8db400479a6/service/github/github.go#L213-L223). Note `githubCommentLine` treats file comments as line==1 for dedupe (github.go:284-290).
- **Commentable test** (done locally, before posting): `filter/filter.go` computes `InDiffContext` by walking every line from start to end and requiring each to map to a line in the parsed diff (`check.InDiffContext && diffline != nil`); "both start and end must be in the same diff hunk" — [filter/filter.go:12-19, 45-60](https://github.com/reviewdog/reviewdog/blob/e784ef04b42944a329d856c69431b8db400479a6/filter/filter.go#L12-L60). `InDiffFile` separates "file in the PR" from "line in a hunk".
- **Fallback tiers**: in-hunk → review comment; file in diff but line outside hunk → file-level comment (`subject_type=file`); file not in diff → not posted to GitHub, written to Actions log/annotations (github.go:144-150). Also overflow comments go into the review `Body` summary (`remainingCommentsSummary`, github.go:313), and a per-request cap (`maxCommentsPerRequest`) is applied to avoid the 403 abuse-detection error (comment at github.go:168-175).
- **Head moving**: a single `g.sha` (the PR head at run time) is used as `commit_id` for everything. Stale comments from earlier runs are matched by fingerprint and deleted unless they have replies (github.go:150-160, 225-233).
- **Errors**: only 403/404 are special-cased (`isPermissionError`, → log fallback in Actions, github.go:205-221); every other error, including 422, is returned as-is.
- Worth borrowing: all-lines-in-one-hunk rule; omit `start_*` for single lines; file-level fallback via `subject_type=file`; summary-body overflow. Avoid: always `RIGHT` (never comments deleted lines).

## microsoft/vscode-pull-request-github — <https://github.com/microsoft/vscode-pull-request-github> (2.6k★, MIT, SHA 8bd445f)
- **Calls**: GraphQL, not REST. `createReviewThread` — [src/github/pullRequestModel.ts:895-950](https://github.com/microsoft/vscode-pull-request-github/blob/8bd445fbeee54d7fbb54b2712b29baa3de9356e5/src/github/pullRequestModel.ts#L895-L950) — runs mutation `addPullRequestReviewThread` with `{ path, body, pullRequestId, pullRequestReviewId: <pending review>, startLine: (startLine === endLine ? undefined : startLine), line: endLine, side, subjectType: (startLine/endLine undefined ? FILE : LINE) }`; falls back to a `LegacyAddReviewThread` mutation without `subjectType` for older GHES (`deleteProps: ['subjectType']`).
- **Pending vs immediate**: always attaches to a **pending review** (`getPendingReviewId` → `startReview` creates `addPullRequestReview` with `commitOID: commitId || this.head?.sha`, pullRequestModel.ts:862-880). A "single comment" is a pending review created and immediately submitted (doc comment at :890-893, `suppressDraftModeUpdate`). Reply path takes an explicit `commitId` (:955-981).
- **Commentable test** (before UI offers it): `getCommentingRanges(diffHunks, isBase)` — [src/common/commentingRanges.ts](https://github.com/microsoft/vscode-pull-request-github/blob/8bd445fbeee54d7fbb54b2712b29baa3de9356e5/src/common/commentingRanges.ts): "For the base file, the only commentable areas are deleted lines. For the modified file, comments can be added on any part of the diff hunk." Base side → ranges of consecutive Delete lines (LEFT); modified side → each hunk's new-line span (RIGHT, includes context). Returned from `provideCommentingRanges` with `enableFileComments: true` ([reviewCommentController.ts:504-515](https://github.com/microsoft/vscode-pull-request-github/blob/8bd445fbeee54d7fbb54b2712b29baa3de9356e5/src/view/reviewCommentController.ts#L504-L515)). So **UI is disabled** outside ranges (VS Code only shows the comment affordance inside them) and a **file-level comment** is offered for the whole file. Debug logs explain "No commenting ranges: …".
- **Head moving**: `commitOID` defaults to `this.head?.sha` (the model's cached head); no re-fetch logic spotted in these paths. Outdated handling comes from GitHub's thread `isOutdated`.
- **Errors**: no 422 message mapping found (`grep` for 422/"Unprocessable"/"must be part of" shows only unrelated merge/assignee cases; "Head branch was modified" only on merge, pullRequestModel.ts:529). `createReviewThread` throws `'Creating review thread failed.'` / `'File has been deleted.'` when the response has no thread.
- **Range UX**: uses VS Code's native Comments API (gutter "+" on commenting ranges, drag/select a range for multi-line); range → `startLine/endLine` via the CommentThread range. This is the editor's built-in behaviour; I did not find custom selection code in the repo. Comment is drafted in an inline editor, with "Add Review Comment" / "Add Single Comment" actions (confirmation = explicit submit button).
- Worth borrowing: LEFT = only deleted lines, RIGHT = whole hunk span incl. context; `startLine` undefined when equal to `line`; `subjectType` FILE/LINE. Avoid: GraphQL requires node IDs and a pending review lifecycle.

## pwntester/octo.nvim — <https://github.com/pwntester/octo.nvim> (3.4k★, MIT, SHA 419e67a)
- **Calls**: GraphQL `addPullRequestReviewThread` with `AddPullRequestReviewThreadInput` (`pullRequestReviewId, body, path, side, line, startSide, startLine`) — [lua/octo/gh/mutations.lua:189-205](https://github.com/pwntester/octo.nvim/blob/419e67aee457406423e7cb4fc41d721ecda61bcd/lua/octo/gh/mutations.lua#L189-L205); built in [lua/octo/model/octo-buffer.lua:600-625](https://github.com/pwntester/octo.nvim/blob/419e67aee457406423e7cb4fc41d721ecda61bcd/lua/octo/model/octo-buffer.lua#L600-L625) (sets `startLine`/`line` only when multi-line). Always inside a **pending review** (`reviewId`), submitted later; it shells out to `gh api graphql`.
- **Commentable test**: `Review:add_comment` — [lua/octo/reviews/init.lua:399-450](https://github.com/pwntester/octo.nvim/blob/419e67aee457406423e7cb4fc41d721ecda61bcd/lua/octo/reviews/init.lua#L399-L450): picks the diff window's side (LEFT/RIGHT), then requires the visual range `[line1,line2]` to sit entirely inside one of the file's precomputed `comment_ranges` (one per hunk); otherwise `utils.error "Cannot place comments outside diff hunks"` (:447). Same "whole range in one hunk" rule as reviewdog.
- **Head moving**: the thread stub carries the `commit` of the diff buffer's side (`layout.left/right.commit`); it is review-level (PR or per-commit) rather than re-resolved at post time. Outdated is read back via `originalCommit`/`originalLine` fields (commands.lua:1592-1604).
- **Errors**: failure callback is `utils.print_err` (raw `gh` stderr shown); no 422 parsing.
- **Range UX**: visual-mode selection in the diff buffer, then a keymap/command (`:'<,'>Octo comment add`, or suggestion variant that pre-fills a ```` ```suggestion ```` block from the selected lines, init.lua:480-488). A draft thread buffer opens next to the diff; the user writes, then saves; nothing is sent until the buffer is saved, and the review is submitted separately.
- Worth borrowing: pre-filled ```suggestion``` block from the selected lines; draft-before-send step. Avoid: Neovim-specific buffers.

## Cross-cutting findings
- **Standalone vs pending**: reviewdog = submitted review (REST) + standalone file comments; vscode-PR & octo = pending review (GraphQL), vscode submits immediately for "single comment". None use the plain REST `POST …/pulls/N/comments` for line ranges except reviewdog's file-level case.
- **Pre-flight commentable check** is universal and local (parse the PR's diff hunks); none rely on catching GitHub's 422. Rule: every line of the range in the same hunk; LEFT only valid for deleted lines, RIGHT for added + context.
- **Fallback when not commentable**: vscode → file-level comment affordance; reviewdog → `subject_type=file`, then log/summary; octo → error message. A general PR comment (issue-comments endpoint) as a quote-fallback was not found in any of the three (reviewdog's analogue is the review `Body` summary).
- **Unverified / gaps**: exact 422 text ("pull_request_review_thread.line must be part of the diff") is not in the docs nor these repos; and VS Code's gutter drag/shift-click is native editor behaviour, not repo code.
